# ACNextGen Native 開発順序

目標は、純正Assetto Corsaの物理へ整合した追加現象を重ね、操作から得られる情報と応答を改善すること。比較対象のシミュレーターと同等という評価は、実装数ではなく再現試験と走行結果で判断する。

主構成は車両データ無編集。共通Physics Worker＋DLLで接続し、車両のdata/script.luaを必須にしない。車両専用アダプターは任意の研究用に限定する。許可・入力・性能の制約と代替案はNO_CAR_SCRIPT_DESIGN_JP.mdを参照。

V4.0では共通Workerの入力と制限付きadditional yaw dampingの出力経路を実装しました。実EXE/DLL・Windows共有メモリ・実Worker Luaによる自動試験は通過し、実ゲームでのAPI受信・挙動・FPS測定が残っています。

## 1. FPSと更新期限

51個の元LuaとC++の同値性を保ち、変数検索、ヒープ確保、監視JSON、ポーリングの負担を減らす。V3.1ではローカル変数を位置で解決し、文字列定数を再利用、通常監視を5項目に縮小する。全信号の検証APIは維持する。

合格条件は、同じ入力に対する数値比較、停止・再開試験、同じ車両・コース・設定でのStop/Resume時のフレーム時間比較。DLLの処理時間とゲームFPSを混同しない。モデルの20Hz達成と物理スレッド相当の高頻度制御も別の基準である。

## 2. 入力の監査

全入力を実測・車両INI・推定・既定値に分け、単位と有効期限を付ける。共通Workerの物理周期入力と描画周期の通常状態を区別する。スリップ角・比、純正Fx/Fy/Mz、ダンパー速度の利用可否と更新時刻を実走で確認する。取得できないlive massを取得済みと扱わない。

欠損入力試験で、元wheel_auditに未定義のclearWheel呼び出しを確認した。wheelsテーブル内の車輪が欠けるとモデルエラーになる。現在のホストは常に4輪のテーブルを作るが、部分欠損対応を追加する際は参照モデル側も明示的に修正する。V3.1ではエラーを隠さず、通常API・軽量APIの両方が同じエラーを報告する試験を追加した。

## 3. 追加現象の契約

各現象に所有モジュール、単位、座標、作用点、反力、上限、必要入力を定義する。タイヤ総力、駆動総トルク、サスペンション総力を純正へ重複加算しない。複数モデルが同じ現象を二重に追加しないようにする。

最初の効果はyaw_moment_budgetのrisk/authorityで調整する追加ヨー減衰です。適用直前の物理速度で非正の仕事率、車体の向き、現在のヨーに対する上限を再確認します。FFBは未接続です。モジュール名やRUNNING表示だけで接続済みとは判定しません。

## 4. 物理側への適用

共通Physics Workerの薄い適用器へ期限付きの追加量を送る。車両ID、セッション世代、sequence、checksumを照合し、Stop、失効、欠損、異常値で解除する。まず1現象・1軸・有限時間で符号と方向を検証する。その後、旋回、制動、加速、縁石の再現試験へ広げる。

## 5. 配布と継続開発

ソース、固定した参照Lua、生成器、テスト、測定結果をGitで保存する。車両MOD本体、ゲームデータ、ローカルのバックアップや実行状態を含めない。GitHubへの公開は実際にアップロードした時点で報告する。

新しいアイディアはIDEAS_JP.mdへ短く置き、実装途中で忘れない形にする。優先順位は性能・入力の正確さ・二重計算の防止・体感評価の順で決める。
