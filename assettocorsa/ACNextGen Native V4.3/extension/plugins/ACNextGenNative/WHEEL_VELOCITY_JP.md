# 車輪速度の計測と精度

2026-10-14に前回の独立確認測定24試行を解析しました。高さ約409 mではfloat32の座標刻みは30.52 µmであり、3 msの差分で1刻みが約0.01017 m/sになります。この値は座標量子化の尺度で、観測された動きすべてが誤差という意味ではありません。

校正WorkerへVELOCITY記録を追加しました。車体の車輪位置における点速度、SDKの車輪velocity候補、レンダー値の経過時間、位置差分の有効性を記録します。車輪velocityの座標系と更新周期は未検証です。世界座標を仮定した比較値は診断専用で、力の出力へ使用しません。

精度解析は `tools/analyze_wheel_velocity.py`、取得は `tools/calibrate_wheel_force.py` を使用します。無効・非有限・順序不正・未完了の記録を拒否するテストと、既存の力の呼び出し回数を変えないテストを通過しています。

新しい対照測定は2回とも車体の起床後に水平速度が停車上限0.005 m/sを超え、64フレームの取得前に終了しました。力の呼び出しは両方0回です。これは速度候補の実ゲーム確認に成功した結果ではありません。次の測定は別の平坦な場所で行います。

その後コースを変更し、停車が落ち着いてから対照測定と引数0.1の8フレーム入力試験を完了しました。両方で64フレームの速度候補を取得しています。新しい場所の高さ座標の刻みは約0.0298 µmで、1刻みを3 msで差分した尺度は約0.00000993 m/sです。対照時の位置差分速度RMSは約0.000114 m/sでした。

世界座標を仮定した「車輪velocity−車体の点速度」のRMSは、対照で約0.000232 m/s、入力試験で約0.000968 m/sでした。一方、入力試験の位置差分速度RMSは約0.0000947 m/sです。単一試験・非同期候補の比較なので力の応答量の認定ではありません。両速度をそのまま同じ減衰入力として扱う根拠はなく、更新周期・座標系と時系列の一致の確認を続けます。新しい場所では高い精度の位置記録を取得できるため、今後の対照比較に使用できます。

通常の追加物理へ復帰し、足回りとLSDの常時適用は保留します。車輪速度の取得精度と力の実効スケールは引き続き未承認です。車両・コースデータの変更はありません。

通常Workerへ座標精度の判定を追加しました。float32の世界位置の丸めを車体上方向へ射影し、差分速度に対する寄与の推定値が0.001 m/sを超える場合、車輪速度の有効ビットを立てません。これにより足回り候補だけを停止し、独立したタイヤ・LSDの計測は継続します。この基準は最大候補係数120 N·s/mに対して0.12 N（12 N上限の1%）に相当します。全誤差の保証や力の単位の承認ではありません。

同じ車輪形状を高さ0.3・16・32・409 mへ移動する試験で、粗い座標だけを拒否することを確認しました。実DLL・EXE・共有メモリ・Worker・物理APIスパイによる停止再開試験も通過しています。実ゲームで足回りを常時適用した検証とは区別します。

tools/capture_wheel_velocity.pyで既存のEnhancementSensorを読み取り専用で開き、物理周期のバイナリを保存できるようにしました。共有メモリを新規作成せず、車両操作・設定変更・力のAPI呼び出しは行いません。checksumsとcommitを確認し、非有限のベクトルを拒否します。生バイトのSHA256と車両hash・epoch・世代も保存します。

停車中の3秒の試行で492サンプルを保存しました。平均更新間隔は約6.07 ms、走行サンプルは0でした。位置の時間差分と、既存の推定速度の時間平均との差は四輪のRMSで約0.000010〜0.000032 m/sです。両方とも関連する変換行列から求めるため、これは独立した速度基準による誤差ではありません。速度を校正済みと扱いません。

走行データが取れたら、tools/analyze_velocity_trace.pyで更新周期・欠測・時間的整合を確認します。独立した速度基準、速度の座標系、力スケールの検証は別途必要です。

## 区間平均からの終端速度上限評価

`wheel_velocity_bound.hpp`にFFB非依存の変換候補を追加した。
真の車輪中心加速度のノルムが過去区間全体でA以下、前後位置の誤差ノルムが
e0/e1以下、時間と座標が認定済みなら、位置差分の区間平均速度に対して
終端速度の誤差ノルムはA*h/2+(e0+e1)/h以下になる。
hはpacketの実前後clock差で、dtとの整合も検査する。
履歴区間の加速度上限は将来の送信/適用区間の上限とは別に必要。

frameのCRC/前後commit、車両/CSP/epoch/世代/番号/鮮度を検査し、
同じ終端時刻・車輪中心・証拠IDの点サンプルへだけ接続する。
既に速度を接続したサンプルへの二重追加を拒否し、誤差を仕事Profileへ加算する。
既存wheel_velocity_verifiedフラグはここでは「認定上限付き推定」を表し、
直接・厳密な瞬間速度の計測を意味しない。direct_instantaneous_measurement=false。
不正時は対象の点/仕事Profileを変更しない。

合成の定加速度運動で終端と平均の差がA*h/2に一致し、位置誤差が加算されること、
別点・別世代・時刻違い・破損・未認定履歴・二重追加を拒否することを確認。
追加減衰の仕事上限へ誤差が反映され、大きい誤差では負の仕事を認定しない試験も通過。
実車のA/e0/e1はまだ認定しておらず、この処理を実ゲームの出力へは接続していない。

`WheelGeometrySensor`を別MMFへ追加した（packet520 B/frame528 B）。
区間と同じ公開番号/epoch/世代/車両/CSP版で終端clockと車体・各輪の原点/3軸を送る。
既存536 B区間packetは変えない。観測器はwheel transformもコピーし、直交性を検査。
Stop/欠測では区間・物質点・幾何の全チャンネルをcommit0へ戻す。
実Lua生成→実Windows MMF→別プロセス記録で3種類のバイト一致を確認した
（CSPの状態API自体は模擬）。ゲーム導入版にはまだ追加していない。

`damper_interval_input.hpp`で区間/幾何frameを照合し、終端の車輪中心に
対応する車体点速度、車体up、車体/各輪の変換行列と、上限付き車輪速度を
点サンプル/候補計算へ接続した。身体側の速度契約と剛体幾何の認定も別途必要。
時刻・文脈・公開番号・原点/up・車輪位置が一致しない組は拒否する。

未認定履歴で停止することを確認した。実車用の認定Profileを作成したわけではない。
